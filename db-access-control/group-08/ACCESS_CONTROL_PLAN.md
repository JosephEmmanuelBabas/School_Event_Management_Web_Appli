# Access-Control Plan - Catering Business Management System

Database: `catering_management_db` (PostgreSQL). Backend: Node.js + Express + `pg` (plain SQL, no ORM).
11 tables in `public` + 1 session table (`session`, used by connect-pg-simple). Identity-column keys, no views, no custom functions or triggers.
Sources: `docs/roles-and-privileges.md` (Activity 3 proposal) and a review of the code in `backend/routes`, `backend/create-admin.js`, `backend/scripts/setup-db.js` and `backend/index.js`.
Passwords are never stored in these scripts.

## Accounts and group roles

| Login account | Group role | App role served | Responsibility | Required privileges |
|---|---|---|---|---|
| existing table owner (e.g. `postgres`) | - | Provisioning | Creates DB and tables (`setup-db.js`), seeds, runs `create-admin.js`; used only for setup/maintenance | Ownership of `catering_management_db` objects |
| `catering_api` | `catering_runtime_grp` | Customer portal / Admin dashboard (enforced by the Express backend) | The only login the running API uses | SELECT on all 12 tables; INSERT + DELETE on 11; UPDATE on 10 (+ 5 columns of `customer`); no write access to `admin` |
| `catering_report` | `catering_readonly_grp` | Reporting | Read non-sensitive records | SELECT on 7 operational tables; column-level SELECT on `customer`, `employee`, `payment`; no `admin`, `session` |
| `catering_ops` | `catering_ops_grp` | Catering operations / staff (proposed) | Look up event details, menus, assignments, inventory | SELECT on 6 tables; column-level SELECT on `customer`, `employee`; no payments, cancellations, `admin`, `session` |

`catering_ops` maps to the `catering_staff` role proposed in `docs/roles-and-privileges.md`. The current backend has no staff login, so **no application code uses it today**; it is a read-only account for people querying the database directly (pgAdmin/psql). Drop it if you do not want it.

## Privilege matrix (what the code actually needs)

| Table | catering_api | catering_report | catering_ops |
|---|---|---|---|
| `admin` | SELECT only | - | - |
| `session` | SELECT, INSERT, UPDATE, DELETE | - | - |
| `customer` | SELECT, INSERT, DELETE; UPDATE on `first_name, last_name, email, phone, address` only | SELECT `customer_id, first_name, last_name` | SELECT `customer_id, first_name, last_name` |
| `employee` | SELECT, INSERT, UPDATE, DELETE | SELECT `employee_id, first_name, last_name, role` | SELECT `employee_id, first_name, last_name, role, phone` |
| `payment` | SELECT, INSERT, UPDATE, DELETE | SELECT all columns except `reference_number` | - |
| `cancellation` | SELECT, INSERT, UPDATE, DELETE | SELECT | - |
| `reservation`, `reservation_menu`, `event_assignment`, `inventory`, `menu_item`, `package` | SELECT, INSERT, UPDATE, DELETE | SELECT | SELECT |

Every row of the matrix is implemented exactly in `02_privileges.sql`.

## Justifications (from the code)
- Admin routes delete from 10 business tables (`customers`, `packages`, `menu-items`, `employees`, `inventory`, `reservations`, `payments`, `reservation-menu`, `event-assignments`, `cancellations`), so DELETE is granted on those and on `session` (logout and expired-session pruning), and nowhere else.
- UPDATE is granted only where code updates, or row-locks with `SELECT ... FOR UPDATE` (`reservation` and `cancellation` in the cancellation and customer-portal payment/cancellation flows; locking needs UPDATE).
- `admin` is read-only for the app: login only does `SELECT`. Admin accounts are created by `backend/create-admin.js`, which must be run as the owner account. A compromised API cannot add, change or delete administrators.
- `customer.password_hash` is never updated by any code path, so UPDATE on `customer` is column-limited. The customer portal login does `SELECT *` (needs `password_hash`), so the runtime keeps full SELECT on `customer`.
- Tables use `GENERATED BY DEFAULT AS IDENTITY`, so INSERT needs no sequence grants (verified).
- Password hashes, contact details, payment reference numbers, admin accounts and session data are hidden from the read-only roles with column-level grants / no grant.
- The `session` table is created by `02_privileges.sql` (as owner, same DDL as the library) so the app account never needs CREATE on the schema. connect-pg-simple's `createTableIfMissing` only checks `to_regclass(...)` and skips creation when the table exists (verified in the code and at runtime).
- All PUBLIC privileges on the database, schema, tables, sequences and functions are revoked; nobody gets CREATE on the schema. New tables get no automatic access.
- Customer vs Admin application roles are enforced by the backend (signed bearer token / `requireAdmin` session), not by PostgreSQL, as the project's own roles document states.

## Findings from reviewing the repo
1. **The app currently runs as a superuser.** `backend/.env.example` sets `DB_USER=postgres`. Anything that gets SQL injection or code execution in the API owns the whole cluster. Switch the running app to `catering_api`.
2. **`database/roles.sql` is much broader than this plan.** It grants `app_runtime_grp` full SELECT/INSERT/UPDATE/DELETE on every table (including `admin`) and does not revoke PUBLIC. It also creates a login named `catering_app`, which is why the new names are `catering_api`, `catering_report`, `catering_ops`. If it was already run, remove the old grant: `REVOKE app_runtime_grp FROM catering_app;` (or `DROP ROLE` the old roles after `REASSIGN/DROP OWNED`).
3. **Not a privilege problem, but a real bug:** `backend/routes/employees.js` inserts/updates a column named `position`, while `schema.sql` and `seed.sql` define it as `role`. `POST /api/employees` fails with `column "position" of relation "employee" does not exist` (observed). Either rename the column in the routes to `role` or add the column; this plan does not change the schema.
4. `create-admin.js` and `setup-db.js` use the same `DB_USER` as the API. Run them as the owner (see below); `catering_api` is intentionally refused on them.

## Run order
1. `01_roles.sql` (as postgres, connected to `postgres`; prompts for 3 passwords)
2. Project setup already done: `schema.sql` + `seed.sql` (e.g. `node scripts/setup-db.js`)
3. `02_privileges.sql` (as the table owner, connected to `catering_management_db`)
4. `04_cluster_hardening.sql` (as postgres, once per cluster; safe to repeat)
5. Run the app as `catering_api` (see "Connecting the app")
6. `.\03_verify.ps1` and screenshot the output

```
psql -U postgres -d postgres -f 01_roles.sql
psql -U postgres -d catering_management_db -f 02_privileges.sql
psql -U postgres -d postgres -f 04_cluster_hardening.sql
.\03_verify.ps1
```

Scripts 01, 02 and 04 are re-runnable.

## Connecting the app
`backend/db.js` reads `DB_USER`/`DB_PASSWORD` from the environment, and dotenv does not override variables that are already set. So in the PowerShell window that starts the API:
```
$env:DB_USER = "catering_api"
$env:DB_PASSWORD = "<your local password>"
npm start
```
(or put the same two values in your gitignored `backend/.env`). For one-time admin tasks, switch back to the owner in that window:
```
$env:DB_USER = "postgres"; $env:DB_PASSWORD = "<owner password>"
node create-admin.js
```

## Verification (57 checks)
`03_verify.ps1` logs in as each account and runs 57 allow/deny checks: 27 for `catering_api` (including 2 connection checks that it cannot reach `postgres` or `template1`), 17 for `catering_report` and 13 for `catering_ops`. Passwords are prompted (or read from `CATERING_API_PW`, `CATERING_REPORT_PW`, `CATERING_OPS_PW` for unattended runs) and never saved.

Result on a PostgreSQL 16 test copy (the project's own `schema.sql` + `seed.sql`), running the actual `03_verify.ps1` under PowerShell 7.4: **57 PASS, 0 FAIL**. Scripts 01, 02 and 04 were also run twice to confirm they are re-runnable.

Application check on the same test copy: the unmodified Express backend was started with `DB_USER=catering_api` and driven end to end (admin login/logout, create/update/delete across all 10 admin routes, and the customer-portal register -> login -> profile update -> reservation -> payment -> cancellation flow). **No `permission denied` errors occurred.** The only failures were the pre-existing `employee.position` bug above (`POST /api/employees`), which is a code/schema mismatch, not a privilege issue.
